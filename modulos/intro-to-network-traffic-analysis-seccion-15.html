Sección 15 Decrypting RDP Connections

El caso: tráfico RDP sospechoso en la máquina de Bob

El equipo de IR capturó tráfico RDP desde el host de Bob hacia otro equipo interno. Mientras se revisaba la imagen forense del equipo, se localizó una clave RDP escondida en una carpeta hive. Combinando esa clave con el PCAP facilitado por la academia (rdp.pcapng dentro de rdp-analysis.zip), es posible romper el túnel TLS que protege la sesión y leerla en claro. El objetivo es responder la pregunta que puntúa en HTB — con qué cuenta se inició la sesión — aplicando el flujo de la sección 14. El laboratorio también menciona el host iniciador, que conservamos como referencia para el informe IR.

!Solo con autorización. Descifrar tráfico ajeno sin permiso del titular es un delito. El laboratorio trabaja sobre el PCAP estático rdp.pcapng y la clave server.key de los recursos opcionales del módulo; nada de esto se comparte fuera del entorno del curso.

Por qué RDP aparece "vacío" en Wireshark

El Remote Desktop Protocol de Microsoft transporta, sobre TCP/3389, un canal de presentación gráfica, entrada de teclado/ratón y redirección de dispositivos. Por defecto, esa sesión va encapsulada dentro de TLS — la negociación usa certificados X.509 del servidor y los cifrados negociados pueden incluir suites forward secrecy (ECDHE/DHE) que cambian las claves en cada sesión. En captura se ven los paquetes TCP y, por encima, TLS + TPKT, pero el cuerpo del protocolo RDP queda oculto bajo el cifrado.

3389

Puerto por defecto. Las implementaciones modernas escuchan en TCP/3389 (y opcionalmente UDP/3389 para RDPUDP, que mejora el transporte pero no sustituye al TCP). Ver una conexión sostenida a este puerto es ya una primera señal de "RDP potencial".

TLS

Cifrado por defecto. El cliente negocia TLS contra el certificado del servidor RDP. A partir del ClientKeyExchange los bytes son opacos para quien no tenga la clave privada.

FS

Forward secrecy. Si se negocian suites ECDHE_* o DHE_*, las claves se generan por sesión y la clave RSA solo firma, no descifra — por eso, en un caso real, no basta con tener la clave.

RSA

Solo con RSA key-exchange. Wireshark puede descifrar TLS si el intercambio es RSA clásico y se le facilita la clave privada del servidor. Es el caso del PCAP del módulo.

El filtro de visualización rdp por sí solo no devuelve casi nada, porque la disección superior queda oculta bajo TLS. Para confirmar que existe tráfico, hay que bajar un nivel:

01-check-3389
Wireshark  filter: tcp.port == 3389verás la conversación TCP: handshake + datos cifradosanalyst@lab:~$ tshark -r rdp.pcapng -Y 'tcp.port == 3389' -q -z conv,tcpuna sola conversación entre 10.129.43.27 y 10.129.43.29:3389

Cómo se consigue la clave RSA de un servidor RDP

En este laboratorio la academia entrega la clave directamente (server.key). En un caso real, el camino es más largo pero vale la pena entenderlo: cuando Wireshark descifra por RSA es porque hemos podido obtener la clave privada de la máquina que actuó como servidor RDP. Sobre Windows, el certificado RDP se almacena en la máquina con su clave privada y se puede exportar.

01

Localizar el certificado. En el servidor RDP abrir certlm.msc → Personal → Certificates → Remote Desktop. Ahí aparece el certificado que el rol RDP usa para negociar TLS.

02

Exportarlo con clave privada. Clic derecho → All Tasks → Export → seleccionar "Yes, export the private key". Formato Personal Information Exchange (.PFX); recordar la contraseña que se le ponga.

03

Pasar a PEM sin contraseña. El servidor RDP descifra TLS cuando Wireshark conoce el material en claro, así que se extrae la clave RSA en formato PEM:

02-key-from-pfx
analyst@lab:~$ openssl pkcs12 -in server.pfx -nocerts -out server.pem -nodesanalyst@lab:~$ openssl rsa -in server.pem -out server.keyserver.key en formato PEM sin contraseña — Wireshark lo aceptará
!El detalle que rompe el descifrado. Si el servidor negocia perfect forward secrecy (cualquier suite con ECDHE o DHE), esta técnica no funciona: la clave RSA nunca se usa para cifrar el tráfico, solo para autenticar. Hay que recurrir al log de pre-master secrets de TLS (SSLKEYLOGFILE) que se describió en la sección 12, o usar una captura con la clave exportada antes de iniciar la sesión.

Task #1 — Abrir el PCAP

Desde los recursos opcionales del módulo, descarga rdp-analysis.zip, descomprímelo y abre rdp.pcapng en Wireshark. Trabaja siempre sobre una copia: el original queda intacto como evidencia y le calculas el hash para la cadena de custodia.

03-open
analyst@lab:~$ cp rdp-analysis/rdp.pcapng work/ && sha256sum work/rdp.pcapngcopia de trabajo + hash para custodiaanalyst@lab:~$ wireshark work/rdp.pcapng

Task #2 — Confirmar que hay tráfico RDP

Antes de tocar nada, confirma dos cosas: que existe una conversación en TCP/3389 entre los dos hosts, y que no puedes ver nada bajo rdp mientras siga cifrado. La combinación de ambas observaciones es lo que justifica el paso siguiente.

04-confirm
Wireshark  filter: rdpprácticamente vacío: el cuerpo va cifrado bajo TLSWireshark  filter: tcp.port == 3389verás la negociación TLS y los datos cifrados hacia/desde :3389analyst@lab:~$ tshark -r rdp.pcapng -Y 'tcp.port == 3389' -q -z conv,tcp10.129.43.27 ⇄ 10.129.43.29:3389 · única conversación sospechosa

Task #3 — Cargar la clave RSA en Wireshark

Wireshark puede descifrar TLS cuando se conoce la clave privada del servidor y el intercambio de claves usado en la sesión no es con forward secrecy. Aquí se cumplen ambas: la academia entrega server.key y el PCAP fue grabado con intercambio RSA clásico. Para que Wireshark la asocie al flujo correcto necesitas cuatro datos exactos.

01

Edit → Preferences → Protocols → TLS. En Wireshark 3.x la entrada se llama TLS; en 2.x es SSL. Selecciona el bloque RSA keys list y pulsa Edit.

+

Añadir entrada. Pulsa + para crear una fila con los cuatro campos siguientes.

IP

IP Address. La IP del servidor RDP. En el PCAP del módulo es 10.129.43.29.

:3389

Port. El puerto donde escucha RDP: 3389.

tpkt

Protocol. Déjalo vacío o escribe tpkt. Es el protocolo de transporte TPKT que RDP usa por encima de TCP; ayuda a Wireshark a asociar la clave al flujo correcto.

KEY

Key File. Apunta a server.key que se entregó con el laboratorio. Acepta y guarda.

↻

Refresca el PCAP. Una vez guardada la clave, fuerza a Wireshark a re-disecar el archivo (View → Reload o cierra y vuelve a abrir). Ahora rdp debería devolver tráfico en claro.

05-key-form
TLS keys list + 10.129.43.29 : 3389 · tpkt · …/server.keyaceptar → guardar → recargar el PCAP

Task #4 — Analizar la sesión RDP en claro

Con la clave cargada, aplicar de nuevo el filtro rdp revela los paquetes del protocolo de aplicación: MCS Connect-Initial, Erect Domain Request, Attach User Request, Channel Join, etc. Es información que, antes del descifrado, no podías ver. Ahora ya puedes: seguir conversaciones TCP reales (no están todas bajo tcp.stream eq 0: las conversaciones TLS internas se reorganizan en subflows), exportar objetos del protocolo y leer directamente la respuesta de Q1 y Q2.

06-decrypted
Wireshark  filter: rdptráfico en claro: PDU types, acciones MCS, Join-Confirm, etc.analyst@lab:~$ tshark -r rdp.pcapng -Y 'rdp' -T fields -e frame.number -e ip.src -e ip.dst -e rdp.pduTypePDU 2 = MCS Connect-Initial · confirma intercambio completo

Cómo responder las preguntas del laboratorio

En este punto ya estás mirando la sesión RDP en claro. El quiz de HTB evalúa solo la pregunta de la cuenta de usuario, que es la única pregunta que suma puntos para completar la sección. El laboratorio también plantea qué host inició la sesión — esa pregunta no puntúa, pero conviene tenerla resuelta porque es la base del informe IR que entregues al equipo.

ⓘ

¿Qué host inició? (informativo). Filtra tcp.port == 3389 y abre Statistics → Conversations, o usa el display filter tcp.flags.syn == 1 && tcp.flags.ack == 0. La IP que envía el primer SYN es el cliente. En este PCAP, el SYN inicial sale desde 10.129.43.27 hacia 10.129.43.29:3389; por tanto, 10.129.43.27 es quien inicia la sesión. No es pregunta de quiz; lo guardas para el informe IR.

Q1

¿Con qué cuenta? (pregunta del quiz). Mantén el filtro tcp.port == 3389 aplicado y busca el registro etiquetado como Ignored Unknown Record. En el panel Packet Bytes, abajo a la izquierda, cambia a la vista ASCII: aparece el nombre de usuario que el cliente intentó autenticar contra el servidor RDP — bucky. Este sí es el único valor que te pedirá el formulario de HTB.

!Por qué existe ese "Ignored Unknown Record". Wireshark intenta disecar como RDP negociaciones que no encajan exactamente con ningún registro estándar del protocolo (extensiones del cliente, BER mal formados, padding del proveedor). En lugar de fallar en silencio, los muestra como Ignored Unknown Record. Aquí el campo útil no es la disección, sino el ASCII sin procesar: el primer campo legible es justo la identidad que el cliente envió.

Línea base y puestos a vigilar

La sección 1 insistía en que sin línea base no se detecta lo raro. Aquí se cumple otra vez: tras añadir la clave y recargar el PCAP, Statistics → Conversations debería mostrar una sola conversación RDP entre los dos hosts. Cualquier conversación extra hacia otros pares sería anómala respecto a esa línea base.

07-baseline
analyst@lab:~$ tshark -r rdp.pcapng -Y 'rdp' -q -z conv,tcpuna única conversación 10.129.43.27 ⇄ 10.129.43.29:3389analyst@lab:~$ tshark -r rdp.pcapng -Y 'tcp.port == 3389 && tcp.flags.syn == 1 && tcp.flags.ack == 0'único SYN sin ACK · confirma quién inicia

Receta reproducible para descifrar tráfico TLS con Wireshark

Lo que acabas de aplicar sirve para cualquier protocolo que se negocie con TLS sin perfect forward secrecy: HTTPS con RSA, SMTP/IMAP con RSA, RDP clásico, LDAPS con RSA, etc. La secuencia, abreviada:

A

Tener la clave privada del servidor en formato PEM sin contraseña (RSA + PEM = server.key). En Wireshark 2.x se llama entrada SSL; en 3.x, TLS.

B

Configurar IP, puerto y protocolo en RSA keys list. Protocolo: http, imaps, smtp o tpkt según el caso; déjalo en blanco si dudas.

C

Recargar el PCAP para que Wireshark vuelva a disecar los registros TLS ya descifrados.

D

Si no descifra: probablemente el servidor negoció ECDHE/DHE — cae a un método alternativo (SSLKEYLOGFILE del cliente o una captura con la sesión ya descifrada).

Por qué esto funciona — y por qué falla en casos modernos

La mayoría de servidores RDP en producción actuales rechazan las suites RSA y obligan a ECDHE, por lo que este laboratorio es un caso de libro: una sesión atrapada cuando la configuración aún era la antigua. En un cliente real nunca deberías apoyarte solo en esta técnica como vía principal de descifrado.

✓

Funciona cuando el intercambio de claves usa RSA clásico, el certificado está disponible y la clave privada es accesible. Típico en sesiones de laboratorio, capturas heredadas y servicios mal configurados.

⚠

Falla cuando se negocia perfect forward secrecy (ECDHE/DHE), cuando se usa TLS 1.3 (siempre PFS), cuando la clave está protegida por HSM/TPM y no se puede exportar, o cuando el cliente no permite las suites RSA.

↑

Alternativa moderna: en lugar de claves RSA, exportar el pre-master secret log con la variable SSLKEYLOGFILE (en navegador o en utilidades que la respeten) e inyectarlo en Wireshark (Edit → Preferences → TLS → (Pre)-Master-Secret log filename).

Lecciones transferibles

Aunque el laboratorio describe una técnica concreta, hay cuatro ideas que reaparecen siempre que trabajes con tráfico cifrado.

≈

La capa de cifrado no es gratis para el analista. Cuando ves un servicio que "no muestra nada" en Wireshark, piensa primero en TLS y verifica por puerto/protocolo; luego decide si puedes descifrarlo.

🔑

La clave controla la lectura. Si tienes material criptográfico del extremo, descifrar es un paso más del flujo; si no lo tienes, dejalo claro y prueba métodos basados en pre-master secrets o en exportación en vivo.

⇄

TCP primero, aplicación después. El handshake y los flags (SYN, SYN-ACK, ACK) identifican al iniciador incluso cuando la capa de aplicación está cifrada. Son los mismos filtros que usaste en la sección 2.

★

El detalle escondido cuenta. El nombre de usuario en Ignored Unknown Record es exactamente el tipo de cosa que se pierde si te quedas solo en la capa superior. Leer el cuerpo en ASCII complementa cualquier disección.

Resumen del laboratorio

Con Wireshark y la clave server.key has pasado de una captura ininteligible a una sesión RDP legible. Lo que has hecho en cuatro pasos — abrir el PCAP, confirmar el puerto, cargar la clave RSA, recargar — es una de las técnicas más potentes del análisis de tráfico: introducir el material criptográfico en la herramienta para iluminar lo oculto. Funciona igual para RDP, HTTPS, IMAPS, SMTP con STARTTLS o cualquier TLS cuyo intercambio no use forward secrecy.

Q1

Which user account was used to initiate the RDP connection?

¿Qué cuenta de usuario se usó para iniciar la conexión RDP?

Respuestabucky
Por qué
Con la clave RSA ya cargada en Edit → Preferences → Protocols → TLS, recargar el PCAP (View → Reload) hace que Wireshark vuelva a disecar los registros RDP. Al aplicar de nuevo tcp.port == 3389, entre los paquetes disecados aparece un registro etiquetado como Ignored Unknown Record. Es un mensaje que no encaja en ningún disector estándar de RDP, y por eso Wireshark lo etiqueta como "ignorado"; pero el contenido sigue siendo legible si cambias la vista de Packet Bytes a ASCII.

1. Mantén el filtro:
tcp.port == 3389

2. Recorre los paquetes hasta localizar uno que en la columna Info diga Ignored Unknown Record (en este PCAP aparece en los primeros registros, durante el intercambio inicial). Selecciónalo.

3. En el panel Packet Bytes, abajo a la izquierda, cambia la vista de Hex a ASCII. La primera cadena legible es el usuario que el cliente intentó autenticar contra el servidor RDP:
bucky

Comprobación por CLI (forma robusta):
tshark -r rdp.pcapng -Y 'tcp.port == 3389' -V 2>/dev/null | grep -i 'Ignored Unknown' -A1Ignored Unknown Record · busca la primera palabra ASCII imprimibletshark -r rdp.pcapng -Y 'tcp.port == 3389' --export-objects 'tls,/tmp/objs' 2>/dev/null; ls /tmp/objs 2>/dev/nullexportar objetos TLS para inspeccionar el cuerpo
Por qué sale como "Ignored Unknown Record". Durante la negociación RDP/MCS pueden aparecer mensajes que Wireshark no sabe disecar limpiamente — extensiones propietarias del cliente, BER abiertos, padding. En vez de fallar, los marca como Ignored Unknown Record y deja el cuerpo en bruto. El campo útil no es la disección: es el primer token ASCII del payload, que es justo el nombre de cuenta.

Por qué no se ve si Wireshark no tiene la clave. Mientras el túnel TLS siga cifrado y Wireshark no conozca el material criptográfico del servidor, esos bytes aparecen como TLS Application Data opaco. Por eso esta pregunta sí depende de haber importado server.key y haber recargado el PCAP.

Idea importante para informes IR. No es solo "qué usuario": saber que bucky se autenticó contra RDP desde 10.129.43.27 une los dos hallazgos y te da un vector de atribución para el ticket de incidente. Eso es precisamente lo que el laboratorio evalúa: juntar el origen del SYN con la identidad que se autenticó.

HTB pide el nombre en inglés, en minúscula y sin decoración: bucky.
